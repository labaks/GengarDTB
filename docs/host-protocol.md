# Протокол ПК-агента (ROADMAP №12)

Дизайн-документ, не код. Закрывает задачу №12: до реализации №13 (клиент на
устройстве) и №15 (агент под Windows) нужен зафиксированный контракт между
ними, иначе оба будут написаны под что-то своё и не сойдутся.

## Зачем это вообще, и почему не по USB

Ради чего устройство стоит рядом с компьютером, а не в любой розетке:
показывать метрики с ПК (загрузка, что играет, статус сборки) и в перспективе
получать уведомления. Транспорт — **WiFi, не USB**: открытие COM-порта дёргает
DTR/RTS и перезагружает плату (см. CLAUDE.md), а любое пробуждение ПК заново
переоткрывало бы порт. USB остаётся только для прошивки и логов.

## Правило автономности (важнее самого протокола)

Агент на ПК может отсутствовать **в любой момент** — ПК спит, выключен,
приложение агента не запущено, сеть моргнула. Это нормальное, ожидаемое
состояние, а не авария:

1. Устройство **не падает** и не блокируется в ожидании агента ни на одном
   этапе (обнаружение, подключение, рукопожатие, подписка).
2. `shell_set_host_connected(bool)` (уже есть в `shell.h`) — единственный
   источник правды для иконки `pc` в тулбаре. Виджет с capability `host`
   при обрыве связи показывает последнее полученное значение с отметкой
   давности, тем же принципом, что и дисковый кеш HTTP-источников (№11) —
   не гаснет и не исчезает из лончера.
3. Планировщик напоминаний (№22) **не зависит от этого протокола вообще** —
   живёт на устройстве, иначе умрёт вместе с компьютером.

## Кто есть кто

- **Агент** — процесс на Windows (№15, ещё не написан). Знает метрики ПК,
  слушает WebSocket, публикует себя через mDNS.
- **Устройство** — ESP32, клиент. Ищет агента через mDNS, подключается,
  переподключается при обрыве. Один активный виджет = один набор подписок
  (см. «Модель на устройстве» ниже) — многоклиентности внутри прошивки не
  требуется, `widget.c` и так открывает не больше одного экрана виджета
  одновременно.

Направление подключения — устройство звонит агенту, не наоборот. Причины:
- переиспользует уже отработанный на этой прошивке паттерн «клиент с
  бэкоффом» (WiFi-реконнект в `net.c`, ретраи HTTP-фетча в `widget.c`)
  вместо нового режима «слушающий сервер на ESP32»;
- на ESP32 не нужен accept-loop и не нужно защищаться от того, что кто
  угодно в сети попробует к нему подключиться — устройство само выбирает,
  к кому идти;
- ПК как более ресурсный конец естественнее выступает точкой, к которой
  подключаются, а не наоборот.

## Обнаружение — mDNS

Агент публикует себя как:

```
Service: _deskos-agent._tcp.local.
Port:    7332            (фиксированный дефолт, см. «Открытые вопросы»)
TXT:     v=1             (версия протокола, см. ниже)
```

Устройство при старте (и при каждом переподключении после нескольких
неудачных попыток по кешированному адресу — см. «Переподключение») делает
`mdns_query_ptr("_deskos-agent", "_tcp", ...)` и берёт первый ответивший
инстанс. Несколько одновременно работающих агентов в сети в v1 не
разруливаются — побеждает первый найденный, это осознанное упрощение, не
забытый случай.

⚠️ **Реализационная деталь для №13**: в ESP-IDF 5.5.5 компонент `mdns` не
входит в ядро (в `components/` его нет) — это компонент менеджера пакетов
(`espressif/mdns` в component registry), подключается как зависимость в
`idf_component.yml`, тем же способом, что уже подключены `esp_lvgl_port`
и `esp_lcd_ili9341`.

## Авторизация — общий токен, не криптография

Модель угроз — своя домашняя сеть, а не враждебная: не нужно защищаться от
активного атакующего в сети, нужно просто не отвечать первому встречному,
кто случайно достучится до порта. Решение — общий секрет, тем же приёмом,
что и WiFi (№8):

**`/sd/agent.json`**: `{"token":"<строка, задаётся при установке агента>"}`.
Нет файла или пустой токен — capability `host` простаивает молча (виджеты
с `host` показывают деградированное состояние), попыток подключения
устройство не делает вообще, как и с WiFi без учётных данных.

Токен передаётся в `hello` (см. ниже) при каждом подключении. Агент,
получив несовпадающий или отсутствующий токен, отвечает `error` и рвёт
соединение до какого-либо обмена данными. Это не защита от прослушивания
трафика (соединение открытым текстом, `ws://`, не `wss://`) — TLS в локальной
сети ради этого не оправдывает сложности (свой CA, установка сертификата на
устройство) при и так тесном бюджете flash (см. CLAUDE.md). Если модель угроз
когда-нибудь изменится (сеть перестанет быть доверенной) — пересматривать
отдельно, не задним числом штопать эту версию.

## Транспорт — WebSocket, JSON текстом

`ws://<ip агента>:<порт>/deskos`. Все сообщения — текстовые JSON-фреймы,
без бинарных фреймов. Управление живостью соединения — нативные
WebSocket ping/pong фреймы протокола, отдельного JSON-сообщения для этого
нет.

### Конверт сообщения

Каждое сообщение — плоский JSON-объект с обязательным полем `type`:

```json
{"type": "...", ...}
```

### Рукопожатие

Устройство, сразу после установления WS-соединения:

```json
{"type":"hello","proto":1,"device_id":"44:1d:64:f3:39:0c","token":"<из agent.json>"}
```

`device_id` — MAC устройства (уже есть в логах, стабилен, не требует
отдельной генерации). `proto` — целое число, версия протокола этого
документа, сейчас `1`.

Агент отвечает одним из двух:

```json
{"type":"hello_ack","proto":1,"agent":"deskos-agent-win","version":"0.1.0","topics":["cpu","now_playing"]}
```
```json
{"type":"error","code":"unauthorized"}
{"type":"error","code":"unsupported_proto","supported":[1]}
```

`topics` в `hello_ack` — список того, что агент **умеет** отдавать прямо
сейчас (зависит от конфигурации агента на этой машине — например,
`build_status` включён не у всех). Устройству эта информация не обязательна
для работы (можно просто попробовать подписаться), но полезна на будущее —
например, для экрана настроек, показывающего доступные темы.

После `error` агент закрывает соединение. Устройство **не пытается
угадать** более старую версию протокола — если `proto` не совпал, это
несовместимость, требующая обновления прошивки или агента, а не деградации
в рантайме. Лечится логом и статусом «pc: incompatible» (см. «Открытые
вопросы» — точный текст статуса не зафиксирован, решается в №13).

### Подписка

Один открытый виджет — один набор тем: `subscribe` **заменяет** предыдущую
подписку целиком, а не дополняет её. Переключение виджета — просто новый
`subscribe` с новым списком (или пустым списком при возврате в лончер):

```json
{"type":"subscribe","topics":["cpu"]}
```
```json
{"type":"subscribed","topics":["cpu"]}
```

Тема, которую агент не поддерживает, молча выпадает из ответного списка
(не ошибка) — та же философия, что у неизвестного фильтра в `ui.jsonl`
(№4): одна нерабочая строка не должна валить всё остальное.

### Данные

Агент шлёт `data` при изменении значения или на собственном интервале
(устройство периодом не управляет — не тот же смысл, что `every` у
HTTP-источников, где именно клиент решает частоту опроса):

```json
{"type":"data","topic":"cpu","ts":1755624000,"value":{"percent":23,"temp_c":54}}
```

`ts` — unix-время на агенте (у ПК есть RTC, в отличие от устройства до
первой SNTP-синхронизации) — задел на будущее для показа возраста данных
по теме, тем же приёмом, что дисковый кеш (№11), если понадобится отдельно
от общего статуса `pc`.

## Модель на устройстве (контекст для №13, не решается здесь)

Один общий клиент — не по одному WebSocket-соединению на виджет. Живёт
рядом с `net` (свой компонент или часть `net`, решается в №13), поднимается
один раз при старте, работает в фоне независимо от того, какой сейчас
открыт виджет:

- новый локальный источник `{"src":"host","topic":"cpu"}` в `ui.jsonl` —
  при открытии виджета подписывает общего клиента на тему `cpu`, при
  закрытии виджета — отписывает;
- входящие `data` для темы `cpu` кладутся в объединённый документ виджета
  под ключ `cpu` — **тот же механизм**, что уже даёт `merge_source()`
  именованным HTTP-источникам (№10). `{{cpu.percent}}` в разметке работает
  без каких-либо изменений в `datasource_resolve()`;
- `shell_set_host_connected()` вызывается из событий этого клиента
  (подключились / потеряли соединение), не из каждого открытого виджета.

## Переподключение

Тот же паттерн бэкоффа, что уже есть в `net.c` для WiFi (`RETRY_MIN_MS`/
`RETRY_MAX_MS`, 2с → 60с с удвоением): при разрыве WS-соединения или
неудаче рукопожатия — реконнект с бэкоффом. Несколько первых попыток — на
закешированный в RAM IP:порт агента (не долбить mDNS-мультикаст на каждый
чих); после нескольких подряд неудач — свежий mDNS-запрос (IP агента мог
смениться, например ПК получил новый DHCP-лиз). Кеш IP не переживает
перезагрузку устройства — своя цена newtork discovery на каждый холодный
старт, но зато корректность важнее: устаревший IP из NVS не стоит той
экономии — mDNS-запрос на холодном старте это разовая, а не постоянная
цена.

## Пример полной сессии

```
device -> agent   {"type":"hello","proto":1,"device_id":"44:1d:64:f3:39:0c","token":"a1b2c3"}
agent   -> device {"type":"hello_ack","proto":1,"agent":"deskos-agent-win","version":"0.1.0","topics":["cpu","now_playing"]}
device -> agent   {"type":"subscribe","topics":["cpu"]}
agent   -> device {"type":"subscribed","topics":["cpu"]}
agent   -> device {"type":"data","topic":"cpu","ts":1755624000,"value":{"percent":23,"temp_c":54}}
...                (виджет закрыт, пользователь вернулся в лончер)
device -> agent   {"type":"subscribe","topics":[]}
agent   -> device {"type":"subscribed","topics":[]}
...                (ПК ушёл в сон — TCP просто перестаёт отвечать)
device: ping без pong в течение таймаута -> считает соединение мёртвым,
        shell_set_host_connected(false), уходит в бэкофф-реконнект
```

## Начальный каталог тем (для №14, не часть протокола)

Сами имена тем и форма `value` — конвенция агента и виджетов, не часть
транспорта: протоколу всё равно, что лежит в `value`, это просто
JSON-значение. Стартовый набор, ориентировочно:

| Тема | `value` | Для чего (№14) |
|---|---|---|
| `cpu` | `{"percent":N,"temp_c":N\|null}` | загрузка системы |
| `now_playing` | `{"title":str,"artist":str,"playing":bool}` | что играет |
| `build_status` | `{"name":str,"state":"ok"\|"failed"\|"running","url":str\|null}` | статус сборки CI |

Список расширяемый — новая тема не требует правки протокола, только
согласия по имени и форме `value` между конкретным виджетом и агентом.

## Что сознательно не решено здесь

- **Порт 7332** — placeholder, не проверялся на конфликты с чем-либо
  типичным в домашней сети. Финализировать при реализации №15.
- **Уведомления с устройства на ПК** или обратные команды (например,
  «поставить на паузу» из виджета) — протокол сейчас однонаправленный
  (агент → устройство). Понадобится — считать отдельным типом сообщения
  вроде `{"type":"command",...}`, не расширять `data` под это.
- **`notify` capability (RGB-LED/динамик, №25)** — не часть этого протокола,
  живёт полностью на устройстве.
- Точный текст статуса `pc` в тулбаре при несовместимой версии протокола
  против «просто не подключено» — решается в №13 вместе с самой реализацией
  индикатора.
- TLS/`wss://` — сознательно не в v1, см. «Авторизация» выше.
